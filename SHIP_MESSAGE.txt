v0.24.0 — THE LOG AS DELIVERED AND THE HISTORIAN: DLIS AND PI WEB API

Two places an operator's data actually lives, and the program now reads
both where they are. A well log is delivered as DLIS; the LAS was the
export, and the strata survey read only the export. The DLIS reader takes
the container as API RP66 V1 lays it out - the storage unit label, the
visible records, the logical record segments and their trailers, the sets
of objects under their templates with every representation code of Appendix
B, the frames and channels, the frame data - with no dependency, and hands
the survey the same stream the LAS port did. It is proven on a real
Schlumberger station log from the public dlisio test set: 104 channels, two
frames, 3,252 records read whole in a tenth of a second, 11 vendor-encrypted
records skipped and named rather than guessed. The survey reads the DLIS
itself now, and refuses a time-indexed frame by name.

The gauge history of most operators sits in a PI System. The PI Web API
port pulls it, GET only: the point by path, the archive between two times
with the server's paging followed to the end, every value with the
archive's own timestamp as the source time and the archive's flags kept -
Good, Questionable, Substituted, not Good, a digital state by its name, a
system state named as the archive's. Credentials come from environment
variables the map names and never from the map; a credential over plain
HTTP is refused in code. On the Patch panel the historian becomes a live
source, the window moving with the last archive time seen.

What it will not do: decrypt; lay out a channel by guess; put a time frame
on a depth axis; write to PI; hold a credential; fill a gap the archive left.

Section BR is new. The gate is 359 checks. The standalone guard is clean.
