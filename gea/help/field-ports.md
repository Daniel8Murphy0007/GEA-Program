# The field ports

> The three links a gauge panel on a pad actually offers, each read-only and each with its own stand-in to rehearse against before the panel is on the line: Modbus RTU on the RS-485 drop (or passed through a serial-to-Ethernet converter), DNP3 from the pad RTU or the pipeline SCADA, and HART-IP from the transmitter itself through a HART-IP gateway. Each is one more protocol on the Patch panel, polled, with every value a record carrying its quality and the rule that set it.

**The command**: `gea modbus-rtu --write-example-config rtu.json` writes the map (the transport - `serial` with the COM port and baud rate, `tcp` for RTU over TCP, `sim` for the stand-in - the unit id, the table, the word order, and the registers with their types, units and the map's source); `gea modbus-rtu --config rtu.json --polls 10` polls it; `--selftest` runs the CRC vectors from the specification and a session against the stand-in. The same for `gea dnp3` (the master and outstation addresses, the points as `ai:<index>`, `bi:<index>`, `ctr:<index>` and the point list's source) and `gea hartip` (the variables as `pv`, `sv`, `tv`, `qv`, `loop_mA` or `dv:<code>` and the device's datasheet as the source). On the dashboard, Patch panel -> Add a patch -> protocol `modbus_rtu`, `dnp3` or `hartip`, Load the example map, Add and start; the supervisor keeps the connection, restarts it with backoff and folds the records into the well's stream like every other patch. The serial transport needs the `serial` extra (`pip install "gea-program[serial]"`); RTU over TCP, DNP3 and HART-IP need nothing.

**What it writes**: per poll, one record per mapped point - the value in the mapping's unit (a HART unit code or a declared `unit_in` converted where a conversion is known), the source time (the outstation's own 48-bit event time for a DNP3 event; the arrival for a static value, a Modbus register or a HART variable, since those carry no clock), the ingest time, the quality and the rule: a Modbus exception, a CRC mismatch or a silent slave is GAP with the fault named; a DNP3 flag that is not ONLINE, or COMM_LOST, OVER_RANGE, REFERENCE_ERR or RESTART, is BAD with the flag named, a FORCED value is kept with the flag in the rule; a HART response code that is an error is GAP, a device status with DEVICE_MALFUNCTION or a variable status that is not GOOD is BAD with the bit named. The patch's state file and records CSV under the well's `records/live/` folder; the summary on the patch page with the faults.

**The number to check**: the samples per minute and the latency on the patch row - for these ports the latency is the poll's own, since the device has no clock - and the `faults` list on the patch page, which should be empty on a healthy line.

**What this page will not call a measurement**: anything written to the device - there is no code path for a Modbus write, a DNP3 control, select or time set, or a HART command that changes a device; a value the device flagged - it is carried as BAD with the flag, never cleaned; a register map or point list this program guessed - every map is the site's with its source, and a port refuses to run without one; a time the device did not send - a static value's time is its arrival, said so in the record; an object this DNP3 master does not parse - the fragment stops there and names the group and variation, nothing is guessed past.
