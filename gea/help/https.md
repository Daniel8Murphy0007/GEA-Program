# HTTPS

> How browsers on the site network reach the control panel without anything in plain text: the site's own certificate (best: the company's certificate authority, which managed computers already trust) or a self-signed one made here; the names it must carry; handing it out; renewal and the expiry alert.

**The command**: Administration -> **HTTPS** (the administrator role): how it stands, the certificate's names, validity, issuer and SHA-256 fingerprint, **Download the certificate**, and under **Change it**: **Use the site's certificate** (the certificate file and its private key, as paths on the machine running the service), **Make a self-signed certificate** (the names it is reached by, the days), **Turn HTTPS off**. A change takes effect at the next start: **Restart** under Operations control. From a terminal: `gea tls --workspace C:\site` prints how it stands; `--site-cert C:\certs\gea-pad3.crt --site-key C:\certs\gea-pad3.key` uses the site's; `--self-signed --name gea-pad3 --name gea-pad3.example.local --name 10.20.0.15` makes one (with no `--name`: this machine's names, localhost and 127.0.0.1); `--off`; `--export-cert C:\certs\gea-site.crt` writes the certificate (never the key) for the site's computers. Then `gea serve --workspace C:\site --host 0.0.0.0` (or the kit's start-dashboard) and open `https://gea-pad3:8765/`.

**What it needs**: for the site's certificate, PEM files: the server certificate first (then any chain), and its private key without a passphrase (the service starts unattended); a `.pfx` is exported to PEM first (`openssl pkcs12 -in gea.pfx -out gea.crt -nokeys` and `-nocerts -nodes -out gea.key`), and the key file is readable by the service's account only. The certificate must carry every name the browsers use - the machine's short name, its full name, its address - as a subject alternative name. The site's files are read where they are, at every start: a renewal put in their place needs only a restart.

**How it is read**: TLS 1.2 is the floor (TLS 1.3 when both ends have it). With HTTPS on, the session cookie is marked Secure, every response tells the browser to use only HTTPS from then on (Strict-Transport-Security, 180 days), and a plain `http://` request on the same port is sent to the same address over HTTPS when it named the machine by a name the certificate carries (otherwise it is told to use HTTPS). Each connection's handshake runs in its own thread, so a scanner or an old client cannot hold up the others. The self-signed certificate is made by this program alone: an RSA key of 2048 bits (3072 on request), an X.509 v3 certificate for a TLS server (not a certificate authority), signed with SHA-256, valid for at most 825 days (Apple's systems refuse a longer one even when trusted by hand). A browser warns about a self-signed certificate until the computer trusts it: by group policy across the site, or by hand (open the downloaded `.crt`, Install Certificate, Local Machine, Trusted Root Certification Authorities) - and the fingerprint shown there is compared with the one on the HTTPS card before it is trusted. A workspace whose certificate files are missing, unreadable or not a pair does not start (`gea doctor` says BLOCK): a site that turned HTTPS on is never served in plain text by surprise. A site already running a reverse proxy can keep TLS there instead (`--behind-proxy`, `gea help upkeep`).

**What it writes**: the setting in `workspace.json` (`control.tls`: the mode, the two files, when and by whom) with the audit lines `tls.site_certificate`, `tls.self_signed` and `tls.off`; for a self-signed certificate, `keys\tls\self_signed_certificate.pem` and `keys\tls\self_signed_key.pem`. The key is never in a report, an export, an evidence pack or a dossier, and the service never sends it; the backup copies it with the rest of the workspace, like the dossier signing key. The alert `tls.expiring` when the certificate is in its last 30 days or has expired, checked every 15 minutes, and cleared when a new one is in place.

**The number to check**: the SHA-256 fingerprint on the HTTPS card against the one the browser shows for the page (the padlock -> the certificate) - the same, or it is not this machine answering; the days left.

**What this page will not call a measurement**: a padlock is not proof of who is answering unless the computer trusts the certificate for a reason - the site's authority, or a fingerprint someone compared. A self-signed certificate encrypts; it does not identify until it is trusted that way.

**Sources**: RFC 8446 (TLS 1.3) and RFC 5246 (TLS 1.2); RFC 5280 (the X.509 certificate and its extensions); RFC 8017 (RSA, PKCS #1 v1.5 signatures); RFC 6797 (Strict-Transport-Security); Apple, "Requirements for trusted certificates in iOS 13 and macOS 10.15" (HT210176: a server certificate valid for at most 825 days, with its names as subject alternative names and the server-authentication key usage).

Related: `gea help upkeep`, `gea help alerts`, `gea help doctor`.
