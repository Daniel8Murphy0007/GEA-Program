# The historian pull

> An operator's gauge history is already in a PI System more often than not, and PI Web API is the sanctioned way out: REST over HTTPS, each PI Point found by its path, its archive read between two times. This port pulls it - read-only, GET only, on the point and stream controllers - and turns every archived value into a record with the archive's own timestamp as the source time, the fetch as the ingest time, and the archive's flags kept.

**The command**: `gea piwebapi --write-example-config pi.json` writes the map: the `base_url` (`https://<server>/piwebapi`), the `auth` (`basic` or `bearer`, with the NAMES of the environment variables that hold the user and password or the token - the map never holds a credential, and a credential is never sent over plain HTTP; `kerberos` through the proxy the site puts in front; `none`), the `mode` (`recorded` - every archived value between `start` and `end`, PI time syntax such as `*-1d` and `*`, paged by the server and followed to the end; `interpolated` at an `interval`; `value` - the current value), and the tags with their PI Point paths (`\\PISRV01\SWD1.DHP`) and the tag list's source. `gea piwebapi --config pi.json --out records.csv --stream-csv stream.csv` pulls once. On the Patch panel, protocol `piwebapi` pulls on an interval, moving the window forward from the last archive time seen, so a historian becomes a live source like a port. `--selftest` and `base_url: sim` run against the stand-in server.

**What it writes**: one record per archived value - the number in the mapping's unit (the point's engineering unit converted where a conversion is known), the archive timestamp as the source time, the fetch time as the ingest time, and the quality: Good is GOOD; Questionable or Substituted is GOOD with the flag in the rule; not Good is BAD with the value kept; a digital state is GAP with the state's name (ON, OFF, Shutdown...); a system state (I/O Timeout, No Data, Pt Created, Calc Failed) is GAP with the state named as a system state; a point the server does not have is GAP with the HTTP status and the server's own error text. The summary: the points found with their names, the records by quality, the faults, the number of calls (paging shows here).

**The number to check**: the record count per tag against what the PI client shows for the same window, and the quality counts - a GAP count that is all digital states on a status tag is right; one that is system states on a pressure tag is the archive telling you the interface was down.

**What this page will not call a measurement**: a value this program wrote to PI - there is no code path that writes a value, creates a point or changes a configuration. A credential in a map - the map names environment variables; a map that holds a password is refused by the convention, and a credential over http:// is refused in code. A digital state as a number - it is carried as the state's name. A gap this program filled - a window with no archived values is a window with no records, and the archive's own system states are passed through as the archive wrote them. A unit this program assumed - the point's engineering unit is what the archive states; a unit with no conversion to the mapping's is BAD with the reason.
