# Live stations (SeedLink)

> The seismic leg has run on records that were already files. The stations do not hand out files; they serve SeedLink - the real-time protocol every data centre and most digitisers speak - and this is the port that takes it: the customer names its stations and channels, says where it left off, and the server pushes each miniSEED record as it is written. SeedLink 3 (the one every SeisComP and ringserver serves) and SeedLink 4.0 (FDSN, 2022) are both spoken; the server's HELLO decides which.

**The command**: `gea seedlink --write-example-config seedlink.json`, then put the server's `host` and `port` (a TexNet station is served by EarthScope at `rtserve.iris.washington.edu:18000`, network `TX`), the stations as `{"network", "station", "selectors"}` with selectors in SeedLink 3 form `LLCCC.T` (`HHZ.D`; `?` for one character; converted for a 4.0 server), and run `gea seedlink --config seedlink.json --seconds 3600 --out live`; the next run resumes from the last sequence number the state file holds. In a workspace: `gea workspace --path C:\site --action add-live-station --name "<display>" --seedlink-config seedlink.json --lat --lon`, then Start on the dashboard's Seismic page (the serving process keeps every enabled live station up and reconnects with backoff) or `--action live-run --station <id>`; `--action live-fold --station <id>` moves the finished day files into the station's record list, and Refresh runs the leg on them. `gea seedlink-sim --port 18000` is a three-component synthetic station to rehearse against; `gea seedlink --selftest` runs both protocols against it on the loopback; `gea seedlink --config ... --hello` prints what a server says of itself.

**What it writes**: every record the server sends, byte for byte, appended to a day file per channel - `NET.STA.LOC.CHA.YYYY.DDD.mseed` - under the station's `live/` folder, and the state beside it: per station the last sequence number (hexadecimal and per station in SeedLink 3, decimal in 4.0; the resume asks `DATA` for the next), per channel the last sample time, the latency (arrival minus the record's last sample), the records, the samples, and the gaps and overlaps between consecutive records (a gap is counted and left, never bridged). A fold moves the day files that are no longer being written (every day but the current UTC day, unless asked) into `source/`, hashes each and appends it to the station's files, vertical channels first, with the audit line naming what was folded; what the leg then computes is computed from what the station sent. The handshake is kept on the state (`HELLO`, the protocol, each `STATION`/`SELECT`/`DATA`, `END`) and the server's own description with it.

**The number to check**: on the live-station card, `CONNECTED` with the latency p95 and the records climbing; after a fold, the station's file count; `REFUSED` with the `STATION` line names a station the server does not have (no reconnection loop); `ENDED` is the server's own `END`.

**What this page will not call a measurement**: a sample across a gap - it is counted and the file keeps the gap. A time the record's header does not carry - the record's own time is the time. A record in a payload format it does not know - counted with the format byte and left undecoded; miniSEED 2 is what is read, miniSEED 3 is named when a 4.0 server sends it. A session the server has ended - the reason is on the state and the port stops. A location or a response - the leg's refresh on the folded files, with a StationXML, is where counts become ground motion.
