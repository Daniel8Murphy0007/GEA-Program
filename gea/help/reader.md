# GEA Reader, for your clients

> One HTML file the site gives its clients: open it in any current browser - Edge, Chrome, Firefox or Safari, on Windows, a Mac or a tablet - drop in a dossier, and it checks the site's signature and every file the way `verify_dossier.py` does, then shows the reports as they were signed. Nothing to install, no Python, no network.

**The command**: Reports tab -> Signed dossiers -> **Download GEA Reader for your clients**, or `gea reader --workspace C:\site --out C:\site\GEA-Reader.html`. Send the file once, by any channel (email, a USB stick, the client's portal); send the site's key fingerprint separately - by phone, email or in the contract - as for any dossier. The client opens GEA-Reader.html, drops a dossier on it (or chooses it), and reads the verdict: **Valid** (signed with the site's key, or with a newer key the site's key handed over to), **Valid, but signed by a key you were not given**, or **Not valid** with the reason. Below the verdict: each check, the signer's fingerprint, the key hand-overs, and every file the dossier holds - a report opens in the page as it was signed, a PDF in the browser's own viewer, a table or a log as text, and any file can be saved. A dossier that lists source records by hash without carrying them lets the client choose their copies and checks each against its hash.

**The program**: for a client who wants it installed, **GEA-Reader-Setup-0.70.0.exe** on the release page installs GEA Reader as a Windows program of its own, for the signed-in user, with no administrator rights and nothing of GEA-Program: GEA Reader in the Start menu and on the desktop with its own icon (a white page with a green seal, on blue) and its own taskbar button, and **Check with GEA Reader** on the right-click menu of .zip files (on Windows 11, under Show more options), which opens the dossier at once. It opens the same page in Microsoft Edge's app window with a browser profile of its own (`%LOCALAPPDATA%\GEA-Reader\window`), so a fingerprint the client saves - **Remember this fingerprint**, with whose it is - stays on that computer, and every later dossier signed with that key reads **Valid** with the name the client gave it. `GEA-Reader-portable-0.70.0.zip` is the same program to unzip and run (`GEA-Reader.cmd`). `python\python.exe -m gea_reader --selftest`, in the installed folder, checks the page, the icon, the taskbar identity and the hand-over of a dossier without opening a window.

**What it writes**: the one file, GEA-Reader.html (about 40 KB): the checks, written in the page's own script - Ed25519 (RFC 8032) in its own arithmetic, SHA-256 from the browser - and, when made from a workspace, the site's name and the fingerprints of every key it has signed with (the current one and each retired one from the key history: public halves only; the signing key never leaves `keys\`). The audit log records each download (`reader.download`) and each `gea reader` (`reader.write`) with the fingerprints the reader carried. The reader page writes nothing on the client's computer but the fingerprints a client saves (in the browser's storage for the page): it reads the zip it is given, in memory, and a saved copy goes where the client's browser saves downloads. The installed program also writes the page it opens to `%LOCALAPPDATA%\GEA-Reader\page` (with the dossier inside it when one was right-clicked; removed ten minutes later) and its right-click entry under the user's own registry keys, removed with the program.

**The number to check**: the page's footer says `self-check: passed` - every time it opens, the reader verifies RFC 8032's three test vectors and refuses a changed message and a changed signature; a browser that cannot hash or unzip is told so and gets no verdict. The fingerprint the reader shows for a dossier is the one `verify_dossier.py` prints and the Reports tab shows. The release's build runs the reader's own script against a set of dossiers - signed, signed after a key hand-over, a report changed, the manifest changed, a file added, a file removed, stored without compression, two entries under one name, not a zip - and requires the same verdict and the same checks, by name and outcome, as `verify_dossier.py` (`tools/reader_fixtures.py`, then `node tools/reader_check.mjs`).

**What this page will not call a measurement**: the trusted time-stamp. A dossier that carries one is marked so, and the reader says it did not check it - that needs the authority's certificates and the computer's trusted roots; `verify_dossier.py` inside the dossier checks it. Who signed: a valid signature shows the files are byte-for-byte what the key's holder signed; the reader names the site only because the fingerprint matches one it was given, and a reader can be passed on by anyone - the fingerprint the client was told separately is what settles who holds the key. That the reports are right: a valid dossier shows they have not changed since signing, not that they are correct. A report's own scripts: a report opens in a frame that runs no script, and the page allows no network request of any kind.

Related: `gea help dossier`, `gea help report-history`.
