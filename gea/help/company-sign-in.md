# Company sign-in

> People sign in to the control panel with the account the company already manages - Microsoft Entra ID, Okta, Google Workspace, Ping, Keycloak or AD FS, by OpenID Connect - so the company's multi-factor, conditional access and leavers apply; the role in GEA comes from the app roles or groups the company gives them. Local accounts stay.

**The command**: Administration -> **Company sign-in** (the administrator role): the issuer, the client id and secret, the redirect URI, the role claim and the role map, a default role, the claim that names the person, the button's words; **Save**, **Test the provider**, **Remove company sign-in**. The sign-in page then shows the button above the local sign-in. From a terminal: `gea oidc --workspace C:\site` prints how it stands; `--issuer https://login.microsoftonline.com/3f8b2c1d-6a4e-4d9b-8c2f-1e7a5b9d0c64/v2.0 --client-id a41c7e92-0d3b-4f6a-9e85-2b6d1c4f7a30 --redirect-uri https://gea-pad3.example.local:8765/api/oidc/callback --secret-from-env GEA_OIDC_SECRET --map GEA.Viewer=viewer --map GEA.Operator=operator --map GEA.Approver=approver --map GEA.Admin=admin` sets it (the secret is read from that environment variable once and kept; `--secret-env NAME` has the service read it at every sign-in instead); `--test` reads the provider; `--pause`; `--off`.

**What it needs**: HTTPS on first (`gea help https`): a provider sends people back only to an https:// address (Entra ID allows http only for localhost). The machine running the service reaches the provider over HTTPS (Entra ID: `login.microsoftonline.com`), and its clock is right to within five minutes. For **Microsoft Entra ID**: in the Entra admin center, App registrations -> New registration - a name ("GEA control panel"), accounts in this organizational directory only, Redirect URI of the Web platform: the control panel's address followed by `/api/oidc/callback`, exactly. Its Overview gives the Application (client) ID and the Directory (tenant) ID: the issuer is `https://login.microsoftonline.com/`, the tenant ID, then `/v2.0` - for a tenant ID of 3f8b2c1d-6a4e-4d9b-8c2f-1e7a5b9d0c64, `https://login.microsoftonline.com/3f8b2c1d-6a4e-4d9b-8c2f-1e7a5b9d0c64/v2.0`. Certificates & secrets -> New client secret: its Value, shown once, is the client secret (it expires: set a reminder to renew it). App roles -> four roles, allowed member types Users/Groups, values `GEA.Viewer`, `GEA.Operator`, `GEA.Approver`, `GEA.Admin`. Enterprise applications -> the same application -> Users and groups: assign people or groups a role (assigning a group needs Entra ID P1 or P2), and under Properties set Assignment required, so only those assigned can sign in. Other providers: an OpenID Connect web application (a confidential client with a secret), the authorization code flow, the same redirect URI, ID tokens signed RS256, and a claim carrying the person's roles or groups.

**How it is read**: "Sign in with your company account" sends the browser to the provider with a fresh state, a nonce and a PKCE challenge (S256); a short-lived cookie binds that sign-in to the browser that started it. The provider sends the browser back with a code, which the service exchanges for an ID token with the client secret and the PKCE verifier, server to server. The ID token is checked with nothing outside the standard library: its RS256 signature against the provider's published keys (fetched again once when a token names a key not yet seen, which is how a provider rotates its keys), the issuer, the audience (this client), the expiry, the issue and not-before times (five minutes of clock difference allowed) and the nonce; any other algorithm, `none` included, is turned away, as is a state used twice or more than ten minutes old. The role is the highest any of the person's values in the role claim maps to; no mapped value and no default role, no sign-in, and the page says which values the person had. With the groups claim, Entra ID sends group object IDs (or the on-premises names for synced groups), and none at all for a person in more than 200 groups - app roles avoid both. The person is kept as a company account in `users.json`, named by the name claim and bound to the provider's subject: it has no password here, its role is set from the claims at every sign-in, an administrator can disable it in GEA, and a local account of the same name is never taken over. A failed company sign-in is audited with its reason; it does not count toward the local sign-in lock (the provider keeps its own), so a mistake in the role map cannot lock an office's local accounts out.

**What it writes**: the settings in `workspace.json` (`control.oidc`) with the audit line `oidc.settings` (and `oidc.off`); the client secret in `keys\oidc_client_secret.txt` (readable by its owner only; never shown, never in a report, an export or a dossier, sent only to the token endpoint) unless an environment variable is named; each sign-in as the audit line `login` with `via: company` and the claim values used, each failure as `login.failed` with the reason; the company accounts in `users.json`.

**The number to check**: **Test the provider** - GOOD, with at least one signing key and RS256 among the algorithms; then a sign-in from a private window by a person with each role, and the role shown at the top right against the role assigned in the company directory.

**What this page will not call a measurement**: who a person is - the company's directory says that, and GEA keeps what its signed token said at the moment they signed in. A person removed from the directory keeps a session already open here until it ends (12 hours) or an administrator revokes it under Live sessions.

**Sources**: OpenID Connect Core 1.0 (sections 3.1 and 3.1.3.7: the authorization code flow and the ID token's checks); RFC 6749 (OAuth 2.0) and RFC 7636 (PKCE); RFC 7515, 7517 and 7518 (JWS, JWK, the RS256 algorithm); RFC 8414 and OpenID Connect Discovery 1.0 (the discovery document); Microsoft, "Redirect URI (reply URL) outline and restrictions" (https required except localhost; at most 256 characters); Microsoft, "Configure group claims for applications by using Microsoft Entra ID" (at most 200 groups in a JWT, object IDs by default).

Related: `gea help https`, `gea help site`, `gea help upkeep`.
